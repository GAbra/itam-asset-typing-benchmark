# Протокол внешней валидации на реальных обезличенных данных

[English](REAL_WORLD_VALIDATION_PROTOCOL.md) · **Русский**

## Назначение

Этот протокол фиксирует правила следующего этапа исследования **до просмотра результатов на реальных данных**. Его задача — проверить внешнюю валидность алгоритма типизации, а не подобрать правила так, чтобы они лучше выглядели на конкретной выгрузке.

Релиз `v2.0.0` считается замороженной синтетической контрольной точкой. Его правила, таксономия, `conflictPriorityWindow=80`, нормализация и логика разрешения конфликтов не изменяются после получения реальных меток задним числом. Любая доработка после анализа реальных данных получает новую версию и сравнивается с неизменённым `v2.0.0`.

## Что является объектом проверки

Единица анализа — **один уже сопоставленный ITAM-актив** с набором наблюдений из доступных источников. Текущий проект не выполняет дедупликацию и не решает задачу entity resolution между AD, Nmap, Kaspersky Security Center, Zabbix, SIEM и другими источниками.

Если исходные записи разных систем связываются до передачи в benchmark, способ корреляции фиксируется отдельно. Ошибки корреляции не должны незаметно учитываться как ошибки классификатора.

## Замороженный baseline

Перед первым запуском на реальных данных в манифест исследования записываются:

- Git tag и commit SHA (`v2.0.0`);
- SHA-256 используемого ruleset;
- версия таксономии;
- `conflictPriorityWindow=80`;
- версия схемы входных данных;
- версия преобразования/обезличивания;
- список доступных источников;
- дата формирования корпуса;
- правила разбиения корпуса;
- заранее выбранные метрики и критерии интерпретации.

После этого baseline считается неизменяемым.

## Подготовка и обезличивание

Реальные исходные данные и таблицы соответствия идентификаторов **не помещаются в публичный Git-репозиторий**.

Минимальные требования:

1. `assetId` заменяется устойчивым псевдонимом, например HMAC от внутреннего идентификатора с секретным ключом, который хранится вне репозитория.
2. Прямые идентификаторы пользователей и инфраструктуры удаляются или преобразуются: ФИО, email, телефоны, логины, hostname/FQDN, IP, MAC, SID/GUID и доменные имена — если конкретный признак не нужен алгоритму.
3. Если структурный признак имени действительно необходим для типизации, сохраняется только необходимая семантика или используется согласованное преобразование, не позволяющее восстановить исходное значение.
4. Точные временные метки при необходимости сдвигаются или округляются так, чтобы сохранялись используемые алгоритмом отношения свежести и порядок наблюдений.
5. Инвентаризационные сведения о ПО, службах и инфраструктуре могут быть коммерчески чувствительными даже без персональных данных; необезличенные строки остаются вне публичного репозитория.
6. Все преобразования фиксируются в версии sanitizer/schema manifest, чтобы один и тот же корпус можно было воспроизвести внутри защищённого контура.

`.gitignore` является только дополнительной защитой от случайного коммита и не заменяет организационные меры контроля данных.

## Ground truth

Эталонная метка формируется **до показа результата классификатора разметчику**.

Для каждой записи должны быть определены как минимум:

- псевдонимный `assetId`;
- эталонный `type`;
- эталонный `subtype`, если он достоверно определим;
- признак `supportedByTaxonomy`;
- статус уверенности/качества разметки;
- при необходимости — причина невозможности достоверно назначить подтип.

Нельзя заставлять разметчика выбирать известный подтип, если объект не укладывается в текущую таксономию. Такие записи нужны для проверки поведения в открытом мире.

Рекомендуется слепая повторная разметка не менее 10% стратифицированной выборки вторым специалистом и последующее разрешение расхождений. Доля согласия и причины расхождений сохраняются в отчёте. Если двойная разметка невозможна, это явно указывается как ограничение исследования.

## Разбиение корпуса и защита от подгонки

Разбиение выполняется **до анализа ошибок алгоритма** по псевдонимному `assetId`, без использования type/subtype и других меток.

Рекомендуемая схема при достаточном размере корпуса:

- 70% — `development`: анализ ошибок и будущая доработка правил;
- 15% — `validation`: выбор между заранее подготовленными вариантами;
- 15% — `locked_test`: финальная проверка, результаты которой не просматриваются до заморозки следующего кандидата.

Конкретные доли и salt фиксируются в манифесте до первого прогона. При слишком малом корпусе схема может быть упрощена, но изменение должно быть принято **до просмотра предсказаний** и описано в отчёте.

На финальном `locked_test` одновременно запускаются неизменённый `v2.0.0` и замороженная следующая версия. После просмотра `locked_test` этот набор больше не используется для дополнительной настройки той же версии.

## Основные метрики

Производительность не является критерием точности. Для внешней валидации отдельно считаются:

- accuracy типа;
- exact type/subtype accuracy;
- precision, recall и F1 для каждого поддерживаемого класса;
- macro-F1;
- confusion matrix;
- `AUTO` precision;
- `AUTO` coverage;
- доля ошибочных уверенных `AUTO`;
- доля `AUTO_TYPE_ONLY`;
- `TYPE_CONFLICT`, `SUBTYPE_CONFLICT`, `NOT_CLASSIFIED` и суммарная abstention rate;
- false-AUTO rate для объектов, помеченных `supportedByTaxonomy=false`;
- метрики отдельно по `DEVICE`, `SOFTWARE`, `ACCOUNT`;
- метрики по заранее определённым группам полноты источников/атрибутов.

`AUTO` precision и `AUTO` coverage всегда публикуются вместе. Нулевая ошибка автоматических решений без указания покрытия не считается достаточной характеристикой качества.

Для долей приводятся 95% доверительные интервалы (например, Wilson interval), для агрегированных метрик вроде macro-F1 — bootstrap 95% CI. Если в классе слишком мало объектов для устойчивого вывода, абсолютное количество записей указывается рядом с процентом.

## Проверка открытого мира

Реальный корпус должен сохранять объекты, которые не представлены текущей таксономией или недостаточно доказаны имеющимися признаками.

Для них правильным безопасным поведением может быть `AUTO_TYPE_ONLY`, конфликт или `NOT_CLASSIFIED`. Уверенное присвоение неподдерживаемого подтипа одному из известных классов учитывается как отдельная опасная ошибка (`false AUTO`).

Неизвестные продукты, устройства и учётные записи не удаляются из выборки только потому, что текущие правила их не знают.

## Что нельзя делать после получения реальных данных

Без выпуска новой версии запрещается:

- менять правила и затем продолжать называть результат результатом `v2.0.0`;
- повторно калибровать `conflictPriorityWindow` на `locked_test`;
- менять таксономию задним числом ради улучшения уже увиденной confusion matrix;
- удалять неудобные классы или неизвестные объекты из denominator без заранее определённого основания;
- смешивать ошибки нормализации/корреляции и ошибки классификации без раздельного отчёта;
- использовать пропуск/abstention для заявления о высокой точности без одновременного указания coverage.

## Порядок исследования

1. Выпустить и зафиксировать `v2.0.0`.
2. Утвердить схему обезличивания и входной контракт.
3. Сформировать независимый ground truth без показа предсказаний.
4. Зафиксировать manifest и детерминированное разбиение.
5. Проверить качество импорта и отсутствие утечки label в признаки.
6. Выполнить baseline-прогон `v2.0.0`.
7. Анализировать ошибки только на разрешённой части корпуса.
8. При необходимости разработать следующую версию правил/таксономии.
9. Заморозить следующего кандидата.
10. Один раз выполнить финальное сравнение на `locked_test`.
11. Публиковать только агрегированные, проверенные на конфиденциальность отчёты и provenance.

## Что можно хранить в публичном репозитории

После отдельной проверки на отсутствие чувствительной информации допускаются:

- агрегированные confusion matrix и метрики;
- количества записей по классам и статусам, если они не раскрывают защищаемую информацию;
- SHA-256/fingerprint обезличенного корпуса;
- версия схемы и sanitizer;
- Git SHA, ruleset SHA-256 и параметры алгоритма;
- методика разметки и разбиения;
- итоговый агрегированный отчёт.

Сырые реальные наблюдения, исходные идентификаторы, таблицы соответствий и секреты псевдонимизации в репозиторий не помещаются.

## Критерий результата

Внешняя валидация должна ответить не на вопрос «можно ли получить высокий процент», а на три отдельных вопроса:

1. насколько точно `v2.0.0` переносится с синтетического мира на реальные данные;
2. при каком `AUTO` coverage система сохраняет приемлемую точность уверенных решений;
3. какие ошибки объясняются правилами типизации, какие — качеством входных данных, а какие — текущими границами таксономии.

До появления такого результата проценты синтетических экспериментов остаются характеристикой контролируемой исследовательской модели, а не production accuracy.
