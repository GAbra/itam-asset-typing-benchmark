# Методика и воспроизводимость

[English](METHODOLOGY.md) · **Русский**

## Исследовательский вопрос

Как три конкретные Java-реализации одних и тех же правил типизации IT-активов соотносятся по совпадению результатов и времени пакетной классификации при росте числа синтетических активов?

Единица входных данных — один нормализованный актив. В эксперименте нет сопоставления активов друг с другом, дедупликации, загрузки через внешние API или записи результата в БД.

## Два baseline — две разные задачи

В репозитории намеренно сохранены два набора результатов. Они отвечают на один функциональный вопрос, но различаются качеством provenance, поэтому их нельзя объединять в одну performance-кривую.

### Исходный архивный baseline

Восемь JSON-файлов в корне `benchmark-results/` — это оригинальный эксперимент 10K / 100K / 500K / 1M, импортированный в commit `e16e158`. Они сохранены без изменений.

| Параметр | Архивный baseline |
|:--|:--|
| CPU / физическая RAM | Не записаны |
| Host OS / Docker / CPU- и memory-лимиты | Не записаны |
| Java / JVM build и фактические флаги | Не записаны; проект ориентирован на Java 21 |
| Правила | версия 1.0.0; 14 канонических правил |
| Seed генератора | 20260909 из исходников/протокола; в старые отчёты не встроен |
| Размеры наборов | 10 000 / 100 000 / 500 000 / 1 000 000 |
| Batch size | 2 000 / 5 000 / 10 000 / 10 000 |

Текущая машина не позволяет задним числом восстановить старую среду. Абсолютные времена исходного эксперимента рассматриваются как исторические наблюдения. Они полезны для сохранения первого эксперимента и для проверки того, что качественный порядок движков не оказался особенностью только более позднего запуска.

Это не доказывает масштабирование по числу правил и не является оценкой production capacity.

## Почему понадобился второй эксперимент

Второй запуск проводился не для замены «неудобных» цифр и не для заявления об оптимизации. Он понадобился потому, что в исходных performance reports не было достаточно данных о среде и исполняемом коде, чтобы сторонний исследователь мог уверенно воспроизвести абсолютные показатели.

Контролируемый baseline закрывает этот пробел: записаны exact image/JAR, CPU- и memory-лимиты, JVM configuration, версия Java, seed, хэши правил и входных данных и точные команды. Исходные файлы оставлены без изменений, поэтому история эксперимента остаётся проверяемой.

Различия между архивными и контролируемыми абсолютными скоростями **нельзя** описывать как ускорение кода. Среда старого запуска неизвестна, следовательно корректного эксперимента «до/после оптимизации» нет.

## Граница измеряемого участка

Для каждого измеряемого прохода JSONL парсится в batch за пределами таймера. Затем каждый движок последовательно обрабатывает один и тот же batch. В timed section входят:

1. Извлечение признаков из нормализованного контекста.
2. Выбор кандидатов и оценка правил.
3. Общий `MatchResolver` и построение результата.
4. Вычисление checksum результата.

Harness суммирует elapsed nanoseconds по batch. Чтение входных данных, создание движков, сериализация отчёта и вычисление input hash находятся за пределами timed section. I/O всё равно может косвенно влиять на кэши, allocation и GC между измеряемыми участками.

`assetsPerSecond = count × 1e9 / elapsedNs`; `nsPerAsset = elapsedNs / count`.

Основной показатель — медиана пяти проходов. Min/max показывают наблюдавшийся диапазон, но не являются доверительными интервалами. Время на актив — это среднее по batch, а не percentile latency отдельного запроса.

XOR checksum в benchmark делает результат наблюдаемым внутри запуска, но не является криптографически устойчивой проверкой корректности. Для стабильного fingerprint между процессами используются SHA-256 из verification report.

## Инициализация

Движки создаются один раз в фиксированном порядке до прогрева. Загрузка канонического YAML учитывается отдельно. Все движки находятся в одной JVM, поэтому более поздние адаптеры могут пользоваться уже прогретой class loading/JIT средой. Startup value — единичное наблюдение стоимости инициализации, а не изолированный cold-start benchmark с множеством повторов.

## Корректность и покрытие

Verification сравнивает тип, подтип, статус и отсортированные идентификаторы выигравших правил для всех движков. SHA-256 каждого движка включает asset ID и эти поля в порядке входных данных. Метки генератора отдельно проверяются по type/subtype.

Все три движка используют общий extractor, канонические правила и resolver. Поэтому согласие движков не способно обнаружить общую ошибку. Метки генератора отражают предположения самого генератора, а не независимую human annotation или production truth.

Дополнительные source tests проверяют пустые признаки, fallback только до типа, конфликты типа/подтипа, forbidden features, disabled rules и дубликаты, возникающие из DMN expansion. Эти проверки относятся к корректности, а не к дополнительным performance workloads.

## Harness version 2

Harness v2 добавляет в отчёты SHA-256 данных, SHA-256 правил, версию ruleset, число включённых правил и порядок движков. Benchmark reports также содержат Java/VM/OS properties, число доступных процессоров, максимальный JVM heap, имена GC и фактическое число записей прогрева.

Контролируемый baseline дополняет эти поля моделью CPU/RAM хоста, Docker/WSL metadata, лимитами контейнера, JVM flags, image ID и SHA-256 JAR в `environment.json`.

Генератор сериализует отсортированные коллекции с LF, чтобы обеспечить стабильные байты между JVM и ОС, и создаёт `.meta.json` с seed/count/distribution. Пустой verification завершается ошибкой, некорректные размеры benchmark отвергаются, а nullable expected subtype обрабатывается безопасно. Алгоритмы движков и канонические правила не менялись просто ради создания baseline v2.

## Ограничения валидности и следующие эксперименты

Фиксированный порядок движков может влиять на cache/GC/JIT эффекты. Прогрева только по префиксу может быть недостаточно. Пять проходов в одной JVM не измеряют вариативность между независимыми процессами. Фоновая нагрузка хоста полностью не контролировалась. Масштабируется только количество активов при неизменных 14 правилах; индексы и DMN table могут вести себя иначе при росте ruleset.

Полезные следующие шаги: независимые JVM forks/JMH, профилирование allocation и GC, рандомизация порядка движков, масштабирование числа правил при фиксированном числе активов, конфликтные/зашумлённые данные и повторные измерения на других документированных машинах. Это будущие эксперименты, а не уже доказанные свойства текущего baseline.
